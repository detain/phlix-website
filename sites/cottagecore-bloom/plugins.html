A Specialist's Shelf

The plugin system is a real contract — not a convention, not a workaround, but a versioned interface that the loader understands and enforces.

The Plugin Model

LifecycleInterface + manifest

Every plugin implements LifecycleInterface, which defines the contract: what the plugin must provide, how it is loaded, how it is shut down, and what metadata it declares about itself. The manifest is a JSON file that describes the plugin to the loader before the plugin code ever runs.

Drop a plugin into the plugins/ directory and the loader finds it, validates the manifest, and starts it. No code changes to Phlix itself, no special loading order, no magic globals.

{
  "name": "my-metadata-provider",
  "version": "1.0.0",
  "entry": "MyMetadataProvider.php",
  "lifecycle_interface": "MetadataProvider",
  "requires": { "phlix": ">=3.0.0" }
}

Ecosystem Plugins

What's already growing

The ecosystem is young but open. The reference implementation is phlix-plugin-example, a minimal working metadata-provider plugin that you can read, run, and extend.

As the plugin contract matures, the community will grow the selection — and because every plugin is discoverable by the loader, a new plugin you write today will load in the same way as one written two years from now.

Write Your Own

Plant something new

The starting point is the plugin example. Clone it, read the LifecycleInterface it implements, edit the manifest, and run composer dump-autoload. Your plugin will appear in the loader output the next time Phlix starts.

If you want a bloom that isn't in the garden yet — a metadata provider for a site Phlix doesn't yet know, a transcoding pipeline for a format that isn't handled, a notification hook for a platform you use — you can plant it yourself.
